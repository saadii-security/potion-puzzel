## Project: Potion Sort Adventure

### Genre: Casual Puzzle / Sorting / Match-Combo / Progression

### Platform: Android first, iOS-ready architecture

# 1. ROLE

You are a senior mobile game designer, game systems designer, Flutter engineer, UI/UX designer, puzzle-game mathematician, monetization designer, and mobile-game product strategist.

Your task is to design and implement a production-quality casual puzzle game called:

# POTION SORT ADVENTURE

The game combines:

1. The simple and satisfying liquid/color sorting mechanic found in Water Sort-style games.
2. The progression, level map, objectives, boosters, blockers, stars, events, and retention systems commonly found in successful match/puzzle games such as Candy Crush.
3. Original potion/laboratory fantasy theming.
4. A strong collection and progression system.
5. Fair monetization without aggressive advertising.

IMPORTANT:

Do NOT create a direct clone of Water Sort, Candy Crush, or any other existing game.

Use only high-level genre conventions and create original:

* mechanics
* visuals
* UI
* level structures
* terminology
* progression
* characters
* artwork
* animations
* economy
* game identity

The final game must feel like its own product.

# 2. CORE GAME VISION

The game should answer this question:

"What if Water Sort had the progression, objectives, boosters, special mechanics, and excitement of a modern puzzle game?"

The player sorts colorful magical potions inside bottles.

However, completing a level is not always simply:

"Sort every bottle."

Levels can have different objectives.

The player must:

SORT → PLAN → COMBINE → CREATE SPECIAL POTIONS → COMPLETE OBJECTIVE → EARN STARS → REWARD → PROGRESS

The game should remain:

* easy to understand
* satisfying
* relaxing
* visually rewarding
* increasingly strategic
* difficult without feeling unfair
* highly replayable

# 4. CORE GAMEPLAY

The basic game board consists of potion bottles.

Each bottle has a fixed capacity.

Example:

Bottle capacity = 4 layers.

A bottle might contain:

RED
RED
BLUE
GREEN

The player taps a bottle and then another bottle.

The game checks whether the move is legal.

A potion may be poured when:

1. The destination bottle has available capacity.
2. The destination is empty OR its top color matches the source's top color.
3. The move does not violate a special mechanic.
4. Any required blocker condition has been satisfied.

When pouring:

* animate the liquid physically
* use smooth transitions
* show liquid movement
* use subtle sound
* avoid instant teleportation

The player should immediately understand what happened.

# 5. WIN CONDITION

The standard level win condition is:

Every normal bottle contains only one color.

Example:

RED RED RED RED
BLUE BLUE BLUE BLUE
GREEN GREEN GREEN GREEN
YELLOW YELLOW YELLOW YELLOW

Empty bottles are allowed where the level definition permits them.

However, not every level should use the standard win condition.

The level engine must support multiple win conditions.

# 8. BOMB POTION

Visual:

A glowing unstable potion.

Function:

When properly completed/activated, it clears a predefined set of potion layers.

Example:

Clear one entire bottle.

Later upgrade:

Clear adjacent bottles.

Do not make this mechanic random.

The player should understand exactly what will happen.

---

# 9. LIGHTNING POTION

Function:

Clears a particular color across multiple bottles.

Example:

Activate blue lightning.

All exposed BLUE layers on the board are removed.

Use carefully because this can make levels trivial.

---

# 10. WILD POTION

A Wild Potion can transform into the required destination color.

Example:

WILD + RED

becomes:

RED

This mechanic should appear later in progression.

---

# 11. FROZEN POTION

Frozen layers cannot be poured until the freeze condition is satisfied.

Possible rules:

* Sort neighboring bottle
* Match required color
* Complete a mini objective
* Use a booster

---

# 12. LOCKED BOTTLE

A bottle displays a lock.

The player cannot interact with it until a condition is met.

Examples:

* Complete another bottle
* Break 3 crystals
* Collect 10 red potions

---

# 13. CRYSTAL BLOCKER

Crystal blocks a layer.

The player must complete a condition to destroy it.

The crystal should visibly crack and break.

Use satisfying animation.

---

# 14. MYSTERY POTION

A hidden potion layer whose color is unknown until exposed.

Important:

Do not make this purely luck-based.

The player should have enough information to make a strategic decision.

---

# 15. PORTAL BOTTLE

Introduced at advanced levels.

A portal connects two bottles.

Pouring through the portal moves potion according to clearly defined rules.

Make the mechanic intuitive.

---

# 16. POISON POTION

Poison cannot freely mix with normal potions.

The player must isolate or dispose of it.

This creates advanced strategic levels.

# 36. LEVEL SOLVER

Every generated level must be verified by a solver.

The solver should determine:

1. Is the level solvable?
2. Minimum/near-minimum number of moves.
3. Search complexity.
4. Whether the level is trivial.
5. Whether the level is excessively difficult.
6. Whether the level has meaningful decision points.

Never publish an unverified level.

# 90. CRITICAL RULES FOR THE DEVELOPMENT AGENT

1. Do not build everything at once.
2. Build the core puzzle engine first.
3. Keep the game deterministic.
4. Keep game logic independent from UI.
5. Do not hardcode levels inside widgets.
6. Do not hardcode economy values throughout the code.
7. Use configuration.
8. Make level generation testable.
9. Build a solver before generating hundreds of levels.
10. Never ship unsolved levels.
11. Do not copy copyrighted assets.
12. Do not clone Candy Crush's visual identity.
13. Do not clone Water Sort's exact UI.
14. Build an original visual identity.
15. Keep ads controlled.
16. Make the game playable without spending money.
17. Protect cloud data.
18. Validate important rewards server-side.
19. Optimize for fun before monetization.
20. Build systems that can support future content.

# 92. SUCCESS CRITERIA

The final product should feel like:

"Water Sort, but evolved into a complete casual puzzle adventure."

A new player should understand the basic mechanic within 30 seconds.

The game should become strategically interesting within approximately 10 levels.

The first special mechanic should appear early enough to prevent repetition.

The player should have a meaningful progression goal.

Players should have reasons to return daily.

Monetization should feel optional rather than forced.

The game should be scalable to thousands of levels.

The architecture should support years of content updates.

# 93. FINAL PRODUCT PRINCIPLE

The most important design principle is:

## SIMPLE TO LEARN.

## HARD TO MASTER.

## SATISFYING TO PLAY.

## REWARDING TO PROGRESS.

The player should open the game thinking:

"I'll play one level."

And naturally end up thinking:

"Okay, one more."

That "one more level" feeling is the primary product goal.

Do not sacrifice it for excessive ads, unnecessary complexity, or aggressive monetization.

Build the game around the satisfaction of:

POUR → SORT → COMBO → SPECIAL POTION → OBJECTIVE COMPLETE → REWARD → UNLOCK → ONE MORE LEVEL.
